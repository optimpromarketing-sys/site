# Редактирование и публикация b24.pro

Главная страница: site ID `238`, landing ID `1604`. `index.html` — блог, а не главная. Папки GitHub не задают маршруты Битрикс24. Проверенные связи перечислены в `deployment-map.json`; пустой block ID означает, что связь не подтверждена и её нельзя использовать для автоматической записи.

Шапка (`1024`) и подвал (`1026`) — общие области. Их публикация влияет на страницы, подключающие эти области. Четыре самостоятельных файла, связанные со старой страницей `1022`, являются фрагментами одного большого HTML-блока. Полный исходник этого блока находится в `legacy/home-1022.html`: замена его отдельным фрагментом удалит остальные секции.

## Изменение существующего блока

1. Прочитать `landing.block.getcontent` в режиме редактирования и опубликованный вариант. Сохранить оба снимка вне репозитория. Если черновик отличается от публикации, выяснить причину до записи. Повторить чтение непосредственно перед записью и остановиться при чужом изменении.
2. Редактировать исходный HTML компонента `bitrix:landing.blocks.html`, а не внешнюю разметку, которую возвращает конструктор. Значение находится в `manifest.nodes["bitrix:landing.blocks.html"].extra.HTML_CODE.VALUE`. Декодировать HTML-сущности один раз и нормализовать окончания строк.
3. Передать `landing.block.updatenodes` структуру `data: {"bitrix:landing.blocks.html": {"attrs": {"HTML_CODE": encodedHtml}}}`. Для `encodedHtml` последовательно экранировать `&`, `<`, `>`, двойные и одинарные кавычки HTML-сущностями. Для апострофа используйте именно `&#39;`: вариант `&#039;` может остаться в отрендеренном JavaScript буквальной сущностью, хотя HTML_CODE при чтении выглядит корректно. Не оборачивать исходник дополнительным `JSON.stringify`. Внешняя структура REST и так сериализуется в JSON.
4. Повторно прочитать компонент и сравнить сохранённый исходник с файлом. Допускается нормализация CRLF и удалённого платформой завершающего перевода строки. Успешный ответ API сам по себе не подтверждает изменение: неверная вложенность параметров может вернуть `true`, оставив код прежним.
5. Проверить JS, взаимодействия и мобильную ширину, затем выполнить публикацию страницы и повторить проверки на публичном URL. Сверить опубликованный HTML_CODE с файлом.
6. Сохранить проверенное изменение отдельным коммитом. При параллельной работе сначала проверить актуальную вершину `main` и не выполнять принудительный push.

Платформа меняет некоторые inline-обработчики, например атрибут `onerror`. Использовать `addEventListener` и проверять фактически сохранённый код. Не применять `updatecontent` к отрендеренному HTML компонента: это другой слой представления.

## Добавление блока или страницы

Для новой секции выбрать подтверждённый landing ID и положение относительно существующего блока (`after_id` по актуальному списку блоков). Назначить уникальный корневой ID; ограничить CSS этим корнем, дать уникальные имена keyframes и SVG-градиентам. JS должен искать элементы внутри своего корня, а повторная инициализация не должна добавлять повторные обработчики. Блок — HTML-фрагмент без второго `html/head/body` внутри страницы.

Для новой страницы отдельно настроить маршрут, заголовок, общие области и навигацию. После создания записать реальные ID в карту, проверить ссылки и опубликовать в рамках согласованного изменения. Не публиковать черновики только потому, что они найдены в репозитории.

Текущий якорь формы на главной: `https://b24.pro/#b28970`. Проверять существование цели перед добавлением ссылки. При переносе секции обновлять одновременно исходник, карту и внутренние переходы.

Для проверки формы достаточно убедиться, что виджет загрузился; отправка тестовой заявки требует отдельной цели проверки, поскольку создаёт обращение в CRM.



## Актуальность материалов и стандартные блоки

Справочники актуализированы 27 октября 2026 года. Отчёты от 7 октября сохраняют свою дату; они не подтверждают состояние страницы после последующих изменений. Новые результаты фиксируются отдельно в `docs/home-validation-2026-10-27.json`.

На главной есть стандартные блоки, не представленные HTML-файлами. Их ID, коды и активность перечислены отдельно в `deployment-map.json`. Просроченный анонс вебинара от 22 октября, заголовок и два разделителя скрыты, а не удалены. Не включать их при восстановлении главной из исходников.

Для обычного блока читайте манифест и обновляйте объявленные селекторы через `landing.block.updatenodes`. Скрытие — `landing.landing.hideblock` с ID черновика. После записи проверьте содержимое и активность повторным чтением, затем публикацию. Сравнивая отрендеренные версии стандартного блока, учитывайте разные служебные ID черновика и публикации, а также пустой опубликованный контент неактивного блока.


Пример экранирования перед записью HTML_CODE:

```javascript
function encodeHtmlCode(source) {
  return source.replace(/&/g, '&amp;')
    .replace(/</g, '&lt;').replace(/>/g, '&gt;')
    .replace(/"/g, '&quot;').replace(/'/g, '&#39;');
}
```

В Python `html.escape(..., quote=True)` создаёт `&#x27;` для апострофа: замените его на `&#39;` перед передачей HTML_CODE. Проверка опубликованной страницы должна подтверждать выполнение JS, а не только равенство декодированного значения в манифесте.
